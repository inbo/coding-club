So, why not trying the DBI function `dbListTables()` to get the names of all the tables? Just try: ``` dbListTables(florabank) ``` 789 tables??? And all that strange names? Well, that's because the `florabank` database is a SQL Server database and the DBI function `dbListTables()` is not able to filter on the default schema `dbo`. So, you get all tables in all schemas and much, much more. --- class: left, top # Intermezzo 1 - database schemas But wait a minute: did I say `schema`?!? what's a *schema*? And why do we have multiple schemas in a database? A schema is a way to **logically group** database objects like tables within a database. It helps organize and manage the database structure, especially in larger databases with many objects. In SQL Server, the **default** schema is **`dbo`**, but other schemas can be created for different purposes or users (check e.g. the INBOVEG database `D0010_00_Cydonia`). And there are also **system schemas**, like **`sys`**, which contain system tables that are used by SQL Server for internal management and operations. System schemas are NOT for user data, but for advanced database management and troubleshooting = never, I say, never touch them unless you are Frederic, Geert, Jo or some very few else from the data management team!* * Typically and luckily we don't even have the rights to modify the sys schema. Still, it's good to know what it is and why we should never touch it :-) --- class: left, top # Intermezzo 1 - database schemas Do you really want to get table names from the dbo schema? Filter on `dbo` using the following code, where we use the function `dbGetQuery()` to run a SQL query on the database connection `florabank`. Notice we have rights to read from the system schema to get the table names and their corresponding schema names. ```r library(DBI) dbGetQuery( florabank, " SELECT s.name AS schema_name, t.name AS table_name -- in sys there is a table, sys.tables, containing all tables information FROM sys.tables t JOIN sys.schemas s ON t.schema_id = s.schema_id WHERE s.name = 'dbo' " ) ``` --- class: left, top # Intermezzo 1 - database views What else can you find in a schema? Well, besides tables, there are also **views**. A view is a kind of "**virtual table**"", a "**saved search*" or a "**saved recipe**" that is based on the result of a SQL query. It looks and acts like a table (you can query it, filter it, join it), but it doesn't store any data of its own. It's just a stored instruction: _"go fetch this specific slice/combination of the real tables, and show it to me as if it were one table."_ How to recognize them? - In RStudio, you cannot open a view of a view 😄 No "table" symbol 𝄜 next to its name in connection pane - Their names typically start with `vw`. Example: the `inbo` schema of INBOVEG database `D0010_00_Cydonia` has no tables, only views. .center[![:scale 30%]({{ site.baseurl}}/assets/images/20260929/20260929_views.png)] --- background-image: url({{ site.baseurl}}/assets/images/background_challenge_2.png) class: left, top # Challenge 2 Use inbodb to: 1. Yes, but you get something like this: ``` obs <- inbodb::get_florabank_observations( florabank, names = c("Impatiens glandulifera", "Hydrocotyle ranunculoides") ) View(obs) ``` .center[![:scale 60%]({{ site.baseurl}}/assets/images/20260929/20260929_view_lazy.png)] --- class: left, top # Intermezzo 2 - R is lazy And you cannot save it as csv file for example: ```r readr::write_csv(x = obs, file = "/data/20260929/obs.csv") > Error in write_delim(x, file, delim = ",", na = na, append = append, col_names = col_names, : is.data.frame(x) is not TRUE ``` Is `obs` not a data.frame??? ```r class(obs) [1] "tbl_Microsoft SQL Server" "tbl_dbi" [3] "tbl_sql" "tbl_lazy" [5] "tbl" ``` All you have is a table (`tbl`), but most of all, it's a **lazy table**. --- class: left, top # Intermezzo 2: R is lazy .center[![:scale 60%]({{ site.baseurl}}/assets/images/20260929/20260929_print_lazy.png)] `obs` is an SQL query, no data are really loaded on your laptop. It is like a **reference** to the result of the query but the full result of the query is not brought into memory. Try also running `obs %>% show_query()`, which shows the SQL query running behind the scenes. --- class: left, top # Intermezzo 2: R is lazy To avoid bad surprises (crashes, out of memory issues, ...), it's good practice to first run your queries lazily. You can fetch the output in two ways: - rerun the inbodb function with `collect = TRUE` - use the `collect()` dplyr function. This will bring the data into memory as a data frame. ```r obs %>% collect() # A tibble: 6,937 × 15 NaamNederlands NaamWetenschappelijk AcceptedNaamWetensch…¹ 1 Reuzenbalsemien Impatiens glandulifera Royle Impatiens glandulifer… 2 Reuzenbalsemien Impatiens glandulifera Royle Impatiens glandulifer… 3 Reuzenbalsemien Impatiens glandulifera Royle Impatiens glandulifer… 4 Reuzenbalsemien Impatiens glandulifera Royle Impatiens glandulifer… 5 Reuzenbalsemien Impatiens glandulifera Royle Impatiens glandulifer… ... # ℹ 6,927 more rows # ℹ abbreviated name: ¹​AcceptedNaamWetenschappelijk # ℹ 10 more variables: ... ``` --- class: left, top # Intermezzo 2 - R is lazy ![:scale 10%]({{ site.baseurl}}/assets/images/20220125/20220125_mister_lazy.jpg) R is not only lazy with databases, R is ALWAYS lazy ```r number <- 5 multiply_by_2 <- function(a, b) { a * 2 # b is not used } multiply_by_2(number) # no value given to argument b ``` `b` is a function argument, but never evaluated, so no error. This is what we mean by being **lazy**: doing **the strict minimum** of evaluation*. For this reason lazy evaluation is sometimes referred as _call-by-need_. **IMPORTANT**: lazy evaluation is a very powerful feature of R, but it can also lead to unexpected behavior if not understood properly. In other words, always make sure that all arguments are used in the function body, unless you have a very good reasons to not do it. * More about lazy evaluation? Give a look at [this tutorial](https://www.r-bloggers.com/2018/07/about-lazy-evaluation/)... or spend a coffeebreak with Thierry ;-) --- background-image: url({{ site.baseurl}}/assets/images/background_challenge_3.png) class: left, top # INTERMEZZO 3 - How to get your data? Not everything is already wrapped in a function. So, how to get your data? Do you know SQL? Excellent! Otherwise, just use dplyr syntax, which is translated into SQL behind the scenes using dbplyr, the database backend of dplyr. Just pay attention to use `tbl()` to connect to the table you are interested to and it will be used as it would be a data frame. Example from the "Use inbodb" section of the [inbodb homepage](https://inbo.github.io/inbodb/index.html): ```r # open database connection con <- connect_inbo_dbase("D0152_00_Flora") # read a whole table dbReadTable(con, "Bron") # query a database using a SQL query dbGetQuery(con, "SELECT ID, Code, Beschrijving FROM Bron") # compose a query using R-code and dplyr syntax tbl(con, "Bron") |> select("ID", "Code", "Beschrijving") |> collect() ``` --- background-image: url({{ site.baseurl}}/assets/images/background_challenge_3.png) class: left, top # Challenge 3 - Templates Feel free to use dplyr syntax or SQL syntax or experiment both! 1.
